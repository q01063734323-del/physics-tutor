# Web Push для «Физики с Егором»

Статус: подготовлено локально в ветке `feature/student-web-push`. На рабочем сайте код, Firestore rules, переменные окружения и расписание не изменялись. Публикация требует отдельного согласования.

## Архитектура и что изменилось

Существующие Next.js App Router, Firebase Authentication / Firestore, кабинеты и домашние работы сохранены. Используется тот же `/sw.js`, манифест и иконки PWA. Пример переменных: `docs/deployment/web-push.env.example`. Новая библиотека — `web-push` 4; `fake-indexeddb` используется только в тестах. Файлы Firebase Admin и существующие секреты не изменялись.

Мутации выдачи, сдачи, изменения срока и проверки теперь проходят через `/api/homework`. Сервер определяет ученика из проверенного Firebase ID token, проверяет активность аккаунта, связь с преподавателем и принадлежность работы. Создание/проверка и событие уведомления записываются в одной Firestore-транзакции. Из клиента убраны прямые записи этих операций. Идентификатор операции переживает потерю HTTP-ответа и перезагрузку страницы; повтор не создаёт вторую домашку/сдачу. Повторное сохранение той же проверки не создаёт новое событие.

`/api/push` обслуживает только подписки текущего ученика, несколько устройств и тест. `/api/push/dispatch` доступен только по отдельному длинному Bearer-секрету расписания. Ответы API имеют `private, no-store`. Публичный VAPID-ключ возвращается ученику через API; приватный ключ никогда не отправляется в браузер. Push endpoints ограничены поддерживаемыми HTTPS-сервисами Apple, Google, Mozilla и Microsoft; произвольные URL и локальные адреса не принимаются.

Новые коллекции, доступные только Admin SDK:

| Коллекция | Назначение |
| --- | --- |
| `pushSubscriptions` | Endpoint, ключи шифрования, аккаунт, устройство, случайная привязка |
| `pushJobs` | Персистентные события и время запуска, прогресс обработки группы |
| `pushDeliveries` | Резервирование и итог каждой пары событие/устройство |
| `pushControl` | Блокировка одновременных запусков диспетчера |
| `pushAssignmentState` | Снимок получателей назначенной работы |

Используются обычные одиночные индексы: `availableAt`, `userId`, `assignmentId`, `teacherId`. Новые составные индексы не нужны, если одиночные не отключались в проекте. Данные не хранятся на эфемерном диске Render. Перезапуск веб-сервиса не стирает очередь.

## Три события

- Назначение: одно событие при создании работы; редактирование названия/условия его не повторяет. При назначении группе сохраняется снимок текущих активных связанных учеников, а не всех пользователей Firebase.
- Срок: событие на `deadline − 24 часа`. Перед отправкой повторно читаются задание и последняя сдача конкретного ученика. Сданные, проверенные и отменённые работы пропускаются; возвращённая на доработку работа остаётся несданной. Изменившийся срок делает старое событие недействительным и создаёт новое. Для работы с исходным сроком менее суток напоминание не создаётся.
- Проверка: итог «Проверено» или «Возвращено на доработку» и изменение комментария/результата создают очередную ревизию события. Неизменённое повторное сохранение не отправляет push. В уведомление не попадают баллы, комментарии, название работы или имя ученика.

Существующая форма выбирает календарную дату. Такая дата означает **23:59 по Москве**; это явно подписано в редакторе. Сервер также принимает дату/время ISO с часовым поясом. Интервал расписания 5 минут означает обычную задержку до следующего запуска, а не точность до секунды. После истечения срока напоминание уже не отправляется.

## Подключение и выход

Кабинет ученика → «Уведомления»: включить устройство, отправить тест, выключить устройство. Разрешение системы запрашивается только при нажатии «Включить». В демо подписка не создаётся.

На iPhone/iPad нужны iOS/iPadOS 16.4+ и приложение, добавленное на экран «Домой»: Safari → «Поделиться» → «На экран Домой», затем открыть с иконки и включить в кабинете. На Android с Chrome включение доступно в кабинете без обязательной установки. Поддержка определяется по API, а инструкция для iOS — дополнительно по платформе. Источник: [WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

При выходе сначала блокируется привязка в IndexedDB service worker, закрываются уже показанные уведомления, выполняются browser unsubscribe и отвязка на сервере; только затем Firebase signOut. При смене аккаунта глобальный защитный компонент также снимает старую локальную подписку. Другие устройства не затрагиваются. При отсутствии сети локальное отключение остаётся в силе; серверная запись может сохраниться до следующего ответа 404/410 и тогда удаляется. Уже принятый внешней службой push отозвать невозможно, поэтому worker дополнительно проверяет случайную привязку текущего аккаунта перед показом и перед открытием.

При нажатии открывается `/student?assignment=ID`; идентификатор сохраняется в URL через вход и перенаправление в кабинет. Работа и её комментарии загружаются через серверную проверку доступа. Чужая работа отвечает 404; пользователь не получает её содержимое. В worker не сохраняются Firebase-токены, оценки, комментарии и HTML домашек.

## Граница гарантий доставки

Web Push не предоставляет транзакцию между нашей базой и внешней push-службой и не доказывает, что телефон показал уведомление. Поэтому обещать безусловную доставку «ровно один раз» нельзя.

Для обычного успешного сценария одно событие имеет одну серверную резервацию на устройство, стабильный notification tag и локальную IndexedDB-дедупликацию. Параллельные задачи и повторные запуска не создают дополнительный push. Перед каждым запросом перепроверяются статус источника и привязка устройства.

- `accepted` — служба приняла запрос; это ещё не подтверждение показа на телефоне.
- `expired` — 404/410; подписка удалена, повторной отправки нет.
- `retry` — явный 429; запрос повторяется не ранее чем через пять минут.
- `uncertain` — сетевой сбой или неопределённая ошибка. Автоматического повтора нет, чтобы не создать дубликат после возможного приёма службой.
- `sending` после аварийного завершения процесса тоже не повторяется автоматически. Это осознанный приоритет защиты от дублей над повторной доставкой сомнительного запроса.

Записи `uncertain`/давние `sending` нужно смотреть в Firestore при разборе проблем. Нельзя массово сбрасывать их в pending: это может повторить уже доставленные push. Между последней проверкой статуса и внешней отправкой существует небольшое неизбежное окно гонки; уже принятый службой push не отменяется задним числом. Проверки выполняются максимально близко к отправке.

## Точные шаги на Render — после разрешения публикации

Проверенная текущая конфигурация: Web Service `physics-tutor`, Free, Oregon; build `npm ci && npm run build -- --webpack`, start `npm start`, health `/api/health`. Ветка сайта сейчас `feature/physics-royale`. Эти настройки при подготовке не менялись.

1. Локально в своём терминале выполнить `node scripts/generate-push-keys.mjs`. Команда выводит публичный/приватный VAPID-ключи и случайный секрет расписания. Не присылать их в чат и не сохранять в Git.
2. В Render → существующий сервис → Environment добавить:

   | Переменная | Значение |
   | --- | --- |
   | `WEB_PUSH_ENABLED` | `false` на первом этапе выкладки |
   | `WEB_PUSH_PUBLIC_KEY` | созданный публичный ключ |
   | `WEB_PUSH_PRIVATE_KEY` | созданный приватный ключ |
   | `WEB_PUSH_SUBJECT` | действующий контакт `mailto:ВАШ_EMAIL` |
   | `PUSH_CRON_SECRET` | созданный случайный секрет, минимум 32 символа |

   Префикс `NEXT_PUBLIC_` для этих переменных не используется. Существующий `FIREBASE_SERVICE_ACCOUNT_JSON`/secret file оставить как есть. VAPID-ключи не генерировать при каждом запуске: смена ключа требует повторной подписки устройств.
3. После согласования перенести проверенную ветку в публикуемую ветку и дождаться Live. Build/start менять не требуется. Не путать это с автоматической публикацией текущих локальных изменений — она пока не выполнена.
4. Проверить на тестовом аккаунте выдачу, сдачу и проверку через новую версию. Обновить открытые PWA: «Обновить»/перезапустить. Подготовленный `firestore.rules` запрещает клиентские записи assignments/submissions и закрывает push-коллекции: опубликовать его только после выкладки нового клиента. Старые открытые версии после ужесточения правил должны обновиться; иначе прямые записи старого клиента будут отклонены. Серверные операции используют Admin SDK. Это важный порядок развёртывания.
5. Выбрать **один** внешний планировщик из вариантов ниже. Не включать сразу два, хотя серверная блокировка защищает от параллельного запуска.
6. Поставить `WEB_PUSH_ENABLED=true` и перезапустить сервис. Убедиться, что планировщик успешно проходит авторизацию.
7. Преподаватель → «Задания» → «Подготовить напоминания для текущих работ»: обрабатываются существующие работы со сроком не менее чем через сутки. Повтор безопасен; старые назначения не объявляются заново.
8. На тестовых телефонах обновить service worker, включить подписки, нажать тест и пройти таблицу приёмки. При закрытой вкладке серверное расписание продолжает работать.

### Вариант A: Render Cron Job

Render → New → Cron Job, тот же GitHub-репозиторий и ветка с этими изменениями:

- Runtime: Node.
- Build Command: `true` (runner использует только встроенный fetch Node; установка зависимостей и сборка Next не нужны).
- Command: `node scripts/dispatch-push.mjs`.
- Schedule: `2-59/5 * * * *` (UTC, каждые пять минут со сдвигом от начала часа).
- Environment: `NODE_VERSION=24`, `PUSH_DISPATCH_ORIGIN=https://physics-tutor-6ytz.onrender.com`, `PUSH_CRON_SECRET` — тот же секрет, что в веб-сервисе.
- VAPID и Firebase credentials в cron **не копировать**: он только вызывает защищённый обработчик веб-сервиса.
- В Runs нажать Trigger Run и проверить успешный код завершения. Cron не печатает секреты или endpoints учеников.

HTTP-запрос поднимает уснувший Free Web Service; runner допускает холодный старт и ограниченно повторяет запрос. Очередь остаётся в Firestore. Такой частый тик обычно не даёт веб-сервису заснуть и расходует бесплатные часы workspace. Возможны холодный старт, перезапуск или задержка: это не расписание с гарантией секунды.

Render Cron оплачивается по активному времени, **минимум $1 за сервис в месяц**, даже при малом использовании. Ничего платного в этой работе не создавалось. Источники: [Cron Jobs](https://render.com/docs/cronjobs), [Free service spin-down](https://render.com/docs/free#spinning-down-on-idle).

### Вариант B: GitHub Actions

Для существующего публичного репозитория стандартный GitHub-hosted runner доступен бесплатно. Шаблон: `docs/deployment/push-schedule.workflow.yml.example`. После согласования скопировать его в `.github/workflows/push-schedule.yml` **на default branch**, добавить Repository variable `PUSH_DISPATCH_ORIGIN` и Actions secret `PUSH_CRON_SECRET`. Скрипт `scripts/dispatch-push.mjs` также должен находиться на default branch. Вручную запустить workflow один раз.

Шаблон сейчас лежит вне `.github/workflows`, поэтому никакого внешнего расписания не включает. У GitHub scheduled jobs возможны задержки/пропуски; в публичном репозитории они автоматически отключаются после 60 дней без активности. Для более предсказуемого расписания рекомендован Render Cron. Источники: [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions), [schedule limitations](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## Проверки и приёмка

`npm run test:push` выполняет детерминированные проверки с подменой Firestore и транспорта, а service worker использует настоящую тестовую IndexedDB (`fake-indexeddb`). Никакие push реальным ученикам тест не посылает.

| Сценарий | Проверка | Среда / результат |
| --- | --- | --- |
| Назначение, два устройства, повтор запуска | Одно событие и одна отправка на каждое устройство, повтор не отправляет | Node, Firestore/transport doubles — проходит |
| Сетевой сбой при сохранении | Повтор использует прежний request ID, а не создаёт вторую работу | Node client/server — проходит |
| Напоминание | Только актуальный срок и несданная работа | Node — проходит |
| Сдача до срока | Нет напоминания | Node — проходит |
| Перенос, отмена, исходный срок менее суток | Старый срок не отправляет, новый пересчитывается, отмена исключается | Node — проходит |
| Проверка/доработка | Нейтральный push, повтор без изменений не отправляет | Node — проходит |
| Чужой аккаунт | Нет чужого push; чтение/сдача/проверка чужой работы запрещены | Node API — проходит |
| Отключение одного устройства | Другие устройства остаются; локальная привязка отключена, подписка снята | Node client/server — проходит |
| Смена аккаунта, повтор одного push, нажатие | Worker отбрасывает старую привязку, подавляет повтор, открывает безопасный URL | VM + IndexedDB — проходит |
| 410, 429, неопределённая сеть | Удаление, отложенный повтор, отсутствие автоматического дубля | Node — проходит |
| Обработка группы частями | Прогресс и отложенная попытка сохраняются между запусками | Node — проходит |
| Реальный iPhone, закрытая PWA | Устройство недоступно | Не проверено |
| Реальный Android, закрытая вкладка | Устройство недоступно | Не проверено |
| Реальные push-службы / VAPID / cron | Не включались до разрешения публикации | Не проверено end-to-end |
| Firestore rules emulator | Эмулятор не запускался | Нужно проверить в staging перед production |

Для телефонной приёмки: два отдельных тестовых ученика A/B, два устройства A. Назначить работу только A, закрыть приложение, дождаться push, открыть его, проверить комментарии после проверки; B не должен получить push или открыть URL A. Отдельной работой проверить 24-часовой срок, сдачу, перенос, отмену и повтор Trigger Run. Завершить выходом на одном устройстве A и убедиться, что другое продолжает получать новые события. До этих действий на реальных устройствах критерии доставки не считаются закрытыми.

Полная сборка/линтер/TypeScript и браузерная проверка UI фиксируются в итоговом отчёте работы. Подготовка к развёртыванию не равна публикации или подтверждению физической доставки.
